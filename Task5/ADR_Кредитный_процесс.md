### **Нефункциональные и архитектурно значимые требования**

- Доступность: все сервисы 24/7, 99.9% uptime (R2, R3, R4, R5).
- Производительность: отклик операций <= 700ms (P2); UI <= 10ms (P3).
- Безопасность: шифрование трафика сайта и ИБ (R6, R7).
- Масштабирование: горизонтально для новых сервисов; АБС масштабируется только вертикально - требуется очередизация и троттлинг (R9, R+8).
- Интеграции: избегать прямых вызовов ИБ к API АБС (R+5); если нужны очереди - использовать Kafka (R+4).
- Данные: условия кредитов - источник истины "Кредитный конвейер" (R+9); кэширование для снижения обращений.
- Поддерживаемость: использовать технологии, уже принятые в банке; приоритет сотрудникам с имеющейся экспертизой (S3–S5).
- Нагрузочное окно: скоринг пред-одобренных - вне рабочих часов (R+10).

### **Решение**

![to_be_containers.png](schemas/to_be_containers.png)

1) Контейнер "Кредитный бэкенд"
- Назначение: единая точка для фронтов (сайт, ИБ) по кредитным операциям; исключает прямой доступ к АБС (R+5).
- Функции: прием заявок; валидация; инициирование СМС-OTP при действиях в ИБ; публикация событий; агрегация и кеширование продуктовых условий из "Кредитного конвейера".
- Хранение: собственный кэш условий (объем малый); долговременные статусы - в профильной БД/хранилище заявок (при необходимости).

2) Контейнер "Адаптер АБС" (расширение уже используемого бэкенда АБС)
- Назначение: прокси/фасад к АБС с троттлингом и очередизацией; упрощает и изолирует интеграции.
- Функции: постановка в очередь команд по заявкам; ограничение RPS; маппинг контрактов; обработка отзывов статусов.

3) Контейнер "Скоринг-воркер"
- Назначение: асинхронная обработка решений по заявкам; поддержка режима "вне рабочих часов" для пред-одобренных скорингов (R+10).
- Функции: подписка на "scoring-requests"; планирование/отложенный запуск; публикация результатов в "credit-status-updates"; политика rate-limit к внешним системам.

4) Интеграции и события (Kafka)
- Темы (минимально достаточные):
    - credit-applications: новые заявки и изменения с сайтов/ИБ/фронт-офиса.
    - scoring-requests: запросы на скоринг/перескоринг, в т.ч. отложенные.
    - credit-status-updates: изменения статусов для уведомлений и UI.
- Причины выбора: декуплинг каналов, выполнение требований к производительности и устойчивости (R+4).

5) "Кредитный конвейер" (источник условий)
- Подход: "Кредитный бэкенд" периодически или по событию обновляет кэш условий; отсутствует кэш в каналах (во избежание рассинхронизации).

6) СМС-шлюз (внутренний сервис банка)
- Использование: подтверждение заявок (OTP) и уведомления статусов (F17, F23, F24).
- Ограничение: изменения в СМС-сервисе выполняет только команда банка (R+3).

7) Технологии
- Для новых сервисов выбран .NET (как и для депозитного кейса) - соответствует текущей экспертизе команды и банк-стеку (S3–S5).

### **Основные потоки**

- Сайт: Клиент подает заявку > "Кредитный бэкенд" валидирует > публикует в credit-applications > "Адаптер АБС"/"Скоринг-воркер" обрабатывают > результат > credit-status-updates > СМС клиенту. Если есть паспортные данные, "Скоринг-воркер" выполняет ускоренный скоринг и отдает решение (F16).
- ИБ: Клиент видит кредиты и пред-одобренный лимит (через "Кредитный бэкенд" и кэш из конвейера) > подает заявку на пред-одобренный кредит > подтверждает СМС-OTP (F21–F23) > дальше как выше; статусы летят в credit-status-updates и в СМС (F24).
- Отделение: Менеджер создает заявку в АБС или продолжает онлайн-заявку (F18–F19). Операции идут через "Адаптер АБС" с очередизацией и троттлингом.

### **Альтернативы**

1) Прямые синхронные вызовы из ИБ/сайта в АБС и скоринг
- Плюсы: простота интеграции.
- Минусы: нарушает R+5; риск перегрузки АБС (R+8); ухудшение отклика под нагрузкой; сниженная отказоустойчивость.

2) Кеширование условий на уровне сайтов/ИБ
- Плюсы: быстрый отклик каналов.
- Минусы: распределенный кеш > риск расхождений; требуется дисциплина команд; повышает связанность. Предпочтительнее единый кэш в "Кредитном бэкенде".

3) Поллинг статусов вместо событий
- Плюсы: проще эксплуатация брокера не требуется.
- Минусы: рост нагрузки; латентность обновлений; хуже масштабируемость. Нарушает целевые NFR по времени отклика.

4) Использовать иной брокер сообщений (например, RabbitMQ)
- Плюсы: зрелый брокер.
- Минусы: противоречит требованию "если нужны очереди - использовать Kafka" (R+4).

### **Ограничения решения**

- АБС масштабируется только вертикально (R+8) - все интенсивные операции должны идти через очереди и с троттлингом.
- Избегать прямых вызовов ИБ > АБС (R+5) - взаимодействие только через "Кредитный бэкенд" и "Адаптер АБС".
- Пред-одобренный скоринг не выполнять в рабочие часы (R+10) - планирование/отложенный режим в "Скоринг-воркере".
- Полная информация об условиях кредитов - только из "Кредитного конвейера" (R+9).
- Изменения в СМС-инфраструктуре выполняет только внутренняя команда банка (R+3).

### **Итого**

Минимально достаточная архитектура добавляет "Кредитный бэкенд", расширяет "Адаптер АБС", вводит "Скоринг-воркер" и ограниченный набор тем Kafka. Это обеспечивает требования по производительности и доступности, снижает нагрузку на АБС, выполняет ограничения R+5, R+8, R+9, R+10 и упрощает эволюцию решения в рамках принятого технологического стека.
